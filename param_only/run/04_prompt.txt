# Parameter Configuration Guidelines – prompt for any EI / function module

Use this prompt to generate **only** the "Parameter Configuration Guidelines" subsection for an SAP Exception Indicator (EI) document. Provide the four input files (or their contents) under the headings at the end, then send the whole thing to the LLM.

---

## Role and task

You are documenting the **Parameter Configuration Guidelines** for an SAP Exception Indicator (EI) / function module. You will receive **four or five** inputs:

1. **Output structure / fields file** – structure (e.g. Excel or table) listing all output fields of the EI.
2. **Parameters (Name (Description)) file** – the **Parameters** sheet from the Available fields Excel for this EI (same as used for the Parameters Reference Table). Contains the full list of parameters for this function.
3. **ABAP code file** – the function module source code.
4. **Selected parameters file: C:\vibe code dev\ei_auto_doc\input\_Parameters.docx


**Your task:** For **every** parameter listed in the Parameters (Name (Description)) file, **in the exact order** of that file, produce a configuration guideline entry. **Group serial-number series** (e.g. KEY1–KEY10, KEY1_DS–KEY10_DS, KEY1_V–KEY10_V, or UVK01–UVK05, UVP01–UVP05, UVS01–UVS05) into one entry with a range heading and one explanation unless business meaning differs by index. Output **only** the "Parameter Configuration Guidelines" subsection. Do not output the Parameters Reference Table, Parameter Relationships, Default Values, Practical Configuration Examples, or any other section.

## How to write each parameter

For **each** parameter (in the order of the Parameters file):

1. **Search first in the Selected parameters file** (`_Parameters.docx`): look up the parameter by name.
   - **If an explanation exists:** Copy it and adjust only the following to match this function’s code and business logic: (a) table and field names (e.g. VBAK vs EKKO), (b) domain terms (e.g. sales order vs purchase order), (c) examples that refer to other EIs or parameters. Keep the structure and the remainder of the explanation unchanged. Do not copy verbatim if the function differs (e.g. purchase vs sales, different date fields).
   - **If no explanation exists:** Write the explanation from the function’s **ABAP code** and **business logic**. Use overall **SAP expertise** only when necessary to clarify meaning (e.g. standard tables, domains, transaction codes).

2. **Use the Output structure / fields file:** Consider all fields from this file. Tie each parameter’s semantics to the function’s **output** (e.g. which fields are filtered, aggregated, or populated). If the link is unclear from the code, use SAP expertise to explain.

3. **Parameter references:** In the main explanation and in Connection subsections, reference **only** parameters that appear in the Parameters (Name (Description)) file for this EI. Do not mention parameters that are not in that file (e.g. do not mention BACKDAYS or DATE_REF_FLD if they are not in the Parameters sheet). If the code or Selected parameters file refers to parameters not in the current function’s parameter list, do not use those names; describe behavior using only parameters that exist in the Parameters file.

4. **Structure of each parameter entry:** Every parameter has a **header** and **at least one sub-section** (the main explanation). Some parameters have **one or two additional** sub-sections. So each parameter has **1–3 sub-sections** in total.

   - **Always (1):** Main explanation – what the parameter does, how it is used in this function, which tables/fields it affects, and how it relates to the output. One or more paragraphs.
   - **Optional (2): Possible values / Options** – Include when the parameter has **specific, non-generic** values that users must choose. Apply these checks for **every** parameter: **(1) Aggregation relevance:** For each parameter, determine if it is aggregation-related by **(a) parameter name** (e.g. AGGR_PERIOD, AGGR_FIELDS, AGG_LVL, DC_IND, agg_type, aggreg_lvl), **(b) parameter description** (e.g. "Aggregation level", "Aggregation fields"), **(c) code** (how the parameter is used: grouping, aggregation logic). If **any** of (a), (b), or (c) suggests aggregation, add "Possible values / Options". Derive values from the code or Parameters file; if no fixed list exists, derive from code (e.g. single record vs aggregated) or state "Values are function-specific; see code or output structure." **(2) Boolean/flag parameters** (e.g. CHAR(1), domain XFELD or similar): **always** add "Possible values / Options" and list **all** possible values used in the code (e.g. **X**: set/active, ** ** (space): not set/inactive; include **0**/**1** if they appear in the code or domain). **(3) Other fixed-option parameters** (e.g. DATE_REF_FLD, STATUS, DURATION_UNIT): add "Possible values / Options". For **DURATION_UNIT**, when it exists in the Parameters file, you **must** use the exact wording specified in the Rules (DURATION_UNIT Options: H, M, D, F with the prescribed labels). For DATE_REF_FLD, possible values are determined from the code or table/structure-specific examples; domain fix values are not authoritative. **(4) Severity, state/color, level, work process type, dialog mode, request/archive status, and user field parameters:** If the **parameter name or description** suggests **severity** (e.g. SEVE_LEVEL, severity, level), **state/color** (e.g. STATE_COLOR, STATE_ICON, color, status), **ordered levels** (e.g. AUDIT_LEVEL, level 1/2/3), **work process type (WP_TYPE)**, **external dialog mode (SLGMODE)**, **request/archive status (RQARCHSTAT)**, or **user field (USER_FLD)**, **always** add a **\[PARAM_NAME] Options:** subsection. For each option give: **value key** (e.g. H, M, L or R, Y, G, B or 1, 2) and a **one-line business meaning** (what it represents and when to use it). When the system maps the key to a numeric value (e.g. 1, 2, 3), include it in parentheses (e.g. "**H** - High severity security events requiring immediate attention (value 3)", "**R** - Red indicating critical security events requiring immediate attention", "**1** - Standard audit level for routine security monitoring"). When the Selected parameters file or domain documentation specifies these values and meanings, use that wording; otherwise derive from code and SAP expertise. **(5) System log / classification and context parameters (CLASID, MONBEW, MONKAT, USTYP, USTYP_DESC, WP_TYPE, SLGTYPE):** When any of these appear in the Parameters file, **always** add **\[PARAM_NAME] Options:** or **Sample values:**; derive values from code analysis (domain, constants, literals) first; if the code does not expose a list, use or adapt the reference sample values in item 5 below. For MONBEW and MONKAT, add a "Work together" note and sample values for both. Do **not** add Options for generic value parameters (e.g. BUKRS, company code, free-text codes) unless they are aggregation-related, boolean, severity/state/level, or one of the parameters in (5). **Default:** Keep the Options list **concise**: each bullet is the **value key** plus a **short label** (or for severity/state/level, value key + one-line business meaning and optional numeric value). **Exception 1 — Parameter in Selected parameters file:** If an explanation (including Options) exists in the Selected parameters file for this parameter, follow that file’s structure and level of detail for the Options subsection; the Options list may be longer if the file specifies it. **Exception 2 — Parameter not in Selected parameters file:** Keep Options short (value key + brief label) except for severity/state/level parameters, where use value key + business meaning (+ numeric value when relevant).
   - **Optional (3): Work together / Connection** – Include when this parameter is **designed to work together** with other parameters in most or all cases. Reference **only** parameters from the Parameters (Name (Description)) file (e.g. BACKMONTHS + COMPMONTHS, DURATION + DURATION_UNIT). Explain how they connect and how to use them together. Decide based on the function code, the Selected parameters file, and SAP expertise. **Navigation / hierarchy strategy:** When parameters form a **navigation, hierarchy, or filtering strategy** (e.g. tree index + tree level + short name, MTE tree, alert hierarchy), add a **Work together / Connection** (or **Navigation strategy** / **How to use together**) subsection that: (1) states the **purpose** in one sentence (e.g. "Enables targeting of specific security monitoring components within the MTE tree structure"); (2) explains how the parameters **interact** (e.g. "MTNAMESHRT targets components; ALIDXINTRE and ALLEVINTRE navigate the hierarchical tree and identify events at specific tree levels"); (3) optionally includes **short configuration examples** (one line per example: `PARAM = value or condition` plus brief purpose), e.g. "MTNAMESHRT = Security - Filter security-related monitoring tree elements", "ALLEVINTRE > 1 - Monitor tree elements beyond the first hierarchical level", "ALIDXINTRE = specific_index - Target specific alert types within tree structure". Use only parameters from the Parameters file in these examples.

5. **System log and classification parameters (sample values from code analysis):** When the Parameters file includes any of **CLASID**, **MONBEW**, **MONKAT**, **USTYP**, **USTYP_DESC**, **WP_TYPE**, **SLGMODE**, **RQARCHSTAT**, **USER_FLD**, or **SLGTYPE**, add a **\[PARAM_NAME] Options:** or **Sample values:** subsection. **Derive values from code analysis first:** search the ABAP code for domain references, constants, literal values, or table/catalog values (e.g. RSLGCLASID, RSLGNKKD, XUUSTYP, work process types). If the code or domain yields a list of values, use those and add a one-line business meaning for each. If the code does not contain a fixed list, use SAP system log / application server expertise and the reference values below as a template; adapt or extend to match the function’s context. For **MONBEW** and **MONKAT**, add a **Work together / Connection** note that they work together for monitoring evaluation and categorization; then list sample values for each. Format: one bullet per value, e.g. `- **key** — Brief business meaning.` Reference (derive from code when possible; otherwise use or adapt):

   - **CLASID (Classification ID):** Provides message categorization for targeted monitoring of specific system log entry types and severity levels. Sample values (from code/domain or adapt): **DB** — Database-related errors and performance issues; **AUTH** — Authorization and security-related messages; **RFC** — Remote Function Call communication issues; **ERROR** — General system error classifications.
   - **MONBEW and MONKAT:** Work together to provide monitoring evaluation and categorization of system log entries. **MONBEW** sample values (priority): **1** — High priority monitoring evaluation; **2** — Medium priority monitoring evaluation; **3** — Low priority monitoring evaluation. **MONKAT** sample values (category): **PERF** — Performance-related monitoring category; **SEC** — Security-related monitoring category; **COMM** — Communication-related monitoring category; **SYS** — System-related monitoring category.
   - **USTYP and USTYP_DESC (User type):** Enable filtering by type of user or process that generated the log entry. **USTYP** sample values: **D** — Dialog users (interactive sessions and transaction processing); **B** — Background users (batch job execution and automated processes); **S** — System users (internal system processes and communication users); **C** — Communication users (RFC and interface processing).
   - **WP_TYPE (Work process type):** Work process type identifier for monitoring specific system components. Sample values: **DIA** — Dialog work processes (user transaction processing and interactive sessions); **BTC** — Background work processes (batch job execution and automated processing); **UPD** — Update work processes (database update processing and transaction completion); **ENQ** — Enqueue work processes (lock management and resource synchronization); **SPO** — Spool work processes (print and output processing).
   - **SLGMODE (External mode of an SAP dialog):** Mode of the session or process that generated the log entry (SAPMODE domain). Sample values: **A** — Dialog (interactive user session); **B** — Background (batch job); **C** — RFC or communication (external/call); **D** — Update; **E** — Enqueue; **F** — Spool; **S** — System. Derive from code (e.g. SAPMODE, R_SLGMODE) when possible; otherwise use or adapt these.
   - **RQARCHSTAT (Request/archive status):** Status of the request or archived object (e.g. job, report). Derive values from code (domain, constants, TBTC*-related or similar); sample values (adapt to context): **A** — Ready for archive; **R** — Released; **F** — Finished; **X** — Cancelled; **P** — Planned. Use code/domain when available.
   - **USER_FLD (User field):** User-defined or system user-field code. Derive values from code (domain, constants, or field catalog); sample values (adapt to context): **USR01** — User group 1; **USR02** — User group 2; or role/authorization-related codes. Use code/domain when available.
   - **SLGTYPE (System log type):** System log message or entry type (e.g. area/subid or message type). Sample values (from code/domain or adapt): derive from code (e.g. RSLGAREA, RSLGSUBID, RSLGTYPE, or structure SLGTYPE); use domain or literal values found in the code. Derive from code when possible.

## Output format (follow exactly)

Output **strictly** the following. Nothing else.

**Single heading:** Use exactly one `### Parameter Configuration Guidelines` line. Do **not** also output `## Parameter Configuration Guidelines` below it (duplicate titles create two headings in Word).

**Structure:** Use **paragraph style** for parameter blocks. Do **not** use list items (no leading `- `) for parameter blocks. Each parameter is a block: one line `**PARAM** (Description from Parameters file):`, a blank line, then one or more paragraphs. For parameters with Options, add a line `**PARAM Options:**` then a **bullet list** (one option per line, e.g. `- **H**: Hours`). For Connection, use a separate paragraph with `**PARAM_A and PARAM_B Connection:**`, or—when the same relationship applies to parallel **table 1 / table 2** pairs (suffix **1** and **2**)—use **`**A1/A2 and B1/B2 Connection:**`** (slashes inside the bold heading) and one short paragraph that states suffix **1** governs the first side and suffix **2** the second.
